# Portfolio readiness record

This is the evidence record for ClaimFlow as a public-source portfolio project. It states what was checked, how, and what was not, so an independent reviewer can judge the public claims. It is not a compliance template, legal advice, or a claim that ClaimFlow is ready for production or real data. The domain model, API guide, testing guide, and AWS architecture remain authoritative for behavior and design; deployment evidence is detailed in [the AWS architecture](aws-architecture.md) and [the testing guide](testing.md), and resource settings in [the infrastructure README](../infrastructure/README.md).

## Scope and operating model

- **Public source, fabricated data.** The source is published as a portfolio and demonstration. The deployment and the local runtime hold only fabricated people, claims, comments, and receipts. No real employee, financial, or receipt data is used, and none may be added.
- **No self-registration.** The operator creates accounts; the Cognito user pool has self-service sign-up disabled.
- **Not a service.** There is no commercial service, production-readiness claim, SLA, customer-support commitment, or compliance claim.
- **Manual, low-cost AWS deployment.** The operator deploys the stack and publishes the web files by hand, in one environment and Region.

Because of this scope, the enterprise controls that apply to real users, real personal data, commercial operation, or production use are **not** being claimed. They are not marked complete anywhere in this record; they are summarized under the trigger that would make them necessary ([Triggers for further work](#triggers-for-further-work)).

## Evidence standard

An item counts as done only when something reproducible or independently inspectable shows it: a file in the repository, a test, a command whose method and scope are recorded, or a dated manual observation with its limits. "The code looks correct," a high test count, "AWS handles it," or a tool's silence is not evidence. Each claim below carries its method and limits; where a check was not run, it says so.

## Deployment and operations evidence

- **Deployment.** The AWS stack (API, authentication, data, hosting, asynchronous processing, alarms) is deployed manually in `ap-southeast-1`. The CDK tests synthesize the stack locally and check the template, not the behavior of deployed resources.
- **Manual browser verification, 21 October 2026.** In a browser against the deployed site: the runtime configuration loads; Cognito PKCE sign-in and the callback work; the protected session, claim list, and claim detail requests succeed; receipt upload, download, replacement, and removal work. The replaced and removed receipts' S3 objects were deleted asynchronously and all four ClaimFlow queues were empty afterwards. This was a manual check, not an automated suite, and only these flows are recorded (details and limits in [the testing guide](testing.md)).
- **Cleanup path.** That evidence supports the publisher → EventBridge → cleanup-worker path only. The receipt janitor, the scheduled outbox sweeper, and the S3 lifecycle rule were not separately verified.
- **Alarms.** 17 CloudWatch alarms and the sweeper's Embedded Metric Format metric are deployed, with ALARM-only email delivery through the `claimflow-alarms` SNS topic. The subscription was confirmed, and a manual `claimflow-api-errors` ALARM transition delivered an email. No OK action is configured, so recovery sends nothing, and the alarm-to-OK transition was not exercised.
- **Not assessed.** Accessibility (beyond static foundations: no automated scan or real keyboard, screen-reader, contrast, zoom, or reflow testing), a threat model and security-verification target, backup restoration, runbooks and incident exercises, load and cost behavior, a release manifest and rollback rehearsal, infrastructure-drift detection, and AWS account safeguards (root and recovery controls, temporary credentials, audit-trail review, budget and cost-anomaly alerts). These controls may exist outside the repository and must be inspected rather than assumed absent or present.

### Third-party notices

`THIRD_PARTY_NOTICES.txt` at the repository root lists 39 packages (35 Lambda, 5 web, `zod` in both) and reproduces the license and notice texts shipped in the installed packages, grouping identical texts. Three `@aws-sdk` packages ship no license file; the file says so and relies on the Apache-2.0 text of their siblings.

- **Delivery.** A Vite plugin (`apps/web/vite.config.ts`, logic in `apps/web/scripts/notices.ts`) runs in every real web build. It reads each Rollup chunk's module list, finds the npm packages and installed versions, and fails the build naming the missing `package@version` values if the file does not list any of them for the web build; only then does it emit the file. `npm run release` also refuses output without it. A command hook on each `NodejsFunction` bundling step copies the file next to `index.js` in every Lambda asset. The hook runs at build time only and leaves no trace in the template, so no resource, permission, runtime behavior, or network call changed.
- **Evidence.** The web check is the plugin, so completeness is verified by building (`npm run build -w @claimflow/web` succeeded on 21 October 2026 and its `dist/THIRD_PARTY_NOTICES.txt` is identical to the root file). `apps/web/test/notices.test.ts` runs fast unit tests of the plugin logic with fake module ids and a temporary directory, and no production build; `apps/web/test/release.test.ts` covers the release check. `infrastructure/test/claimflow-stack.test.ts` checks that every synthesized Lambda asset contains an identical copy, that the file lists every package esbuild bundles for the five handlers, and that the template does not mention it. A synth on 21 October 2026 produced all five assets with the file.
- **Limits.** It covers only what these two kinds of artifact bundle; the Node.js and Lambda runtimes, AWS services, dev and build tools, and the local runtime's packages are outside it. The file was generated once by an uncommitted script and must be regenerated by hand when a bundled dependency changes; nothing flags stale extra entries. The built JavaScript has no license comments, so the notice is the separate `/THIRD_PARTY_NOTICES.txt` beside it, not linked from the page. The Lambda test mirrors, but is not identical to, CDK's esbuild invocation. The deployed web files do not yet include the notice (unresolved item 3).

### Secret scan

**Gitleaks 8.30.1, 22 October 2026.** A recognized scanner was run with its built-in default rules and no custom configuration. It was not installed in the repository: the official Windows release archive was downloaded to a temporary directory outside the repository and checked against the SHA-256 value in the release's published checksums file, and no dependency, `package.json`, or lockfile was touched. Findings were redacted in the output.

- **History scope.** `gitleaks git` over every commit reachable from all refs: 65 commits (about 3.4 MB) across the local branches `main`, `archive/pre-rebuild`, and `rebuild/claimflow` and the remote-tracking refs `origin/main` and `origin/HEAD`; there are no tags.
- **Working-tree scope.** `gitleaks dir` over a copy of the 282 files that Git lists as tracked or untracked and not ignored, so uncommitted work and new files were included. Ignored directories (dependencies, build output, coverage, CDK output, and `.local/`) were excluded, as the copy contained none of them.
- **Result.** The history scan reported 2 findings and the working-tree scan 4, all rule `generic-api-key`. Each was investigated: all are the same 17-character, lower-case-and-digit literal in test files (`services/api/test/aws-claim-mutations-api.test.ts`, two lines, and `services/api/test/aws-category-api.test.ts`, two lines), used as the `key` of idempotency records in fake-store tests. It is a fixture identifier that grants access to nothing, not a credential. The two history findings are the `aws-claim-mutations-api.test.ts` lines in commit `7ca9853`; `aws-category-api.test.ts` is not yet committed, which accounts for the extra two working-tree findings. No other finding was reported, and nothing was modified or allow-listed: no `.gitleaksignore` or configuration was added, so a future Gitleaks run will report these lines again unless an allowlist is chosen.
- **Not covered.** Ignored files, and commits or objects not reachable from a ref in this clone (reflogs, stashes, unreferenced objects). Anything outside this clone: GitHub's own copies, forks, pull-request refs, caches, and any other repository clone. Files Gitleaks does not decode (for example compressed or binary content). Secrets that its default rules and entropy checks cannot recognize. GitHub secret scanning was not consulted or verified.
- **Final rerun.** The same verified release, redaction, and scopes were run again later on 22 October 2026, after the last documentation and package-metadata changes: the same 65 commits and 282 working-tree files, and identical results (2 history and 4 working-tree findings, all the same idempotency-key fixture literal in the same test lines). Nothing else was reported.
- **Currency.** The scan reflects the commits and the uncommitted working tree as of the final rerun. Any later commit or change is unscanned.

An earlier ad hoc check (21 October 2026, `git grep` over the same refs and the working tree) looked for specific patterns: AWS access-key IDs, private-key headers, GitHub and Slack tokens, JWT-shaped strings, AWS secret-key variable names, quoted credential assignments, ARNs with a 12-digit account ID, the deployed account ID, the Cognito user-pool ID format, the operator's personal email address, and any email address, plus a file-name search for `.env`, key and certificate files, the local session secret and database, `cdk.out`, and credential files. It found nothing beyond fictional test-fixture text, the documentation placeholder account `123456789012`, and `example.com` addresses, and none of those sensitive file names was ever committed. It is not a recognized scanner and is kept only as a complement to the Gitleaks run; the 19 October audit also reported no common credential patterns.
