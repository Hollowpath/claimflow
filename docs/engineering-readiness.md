# Portfolio readiness record

This is the evidence record for ClaimFlow as a public-source portfolio project. It states what was checked, how, and what was not, so an independent reviewer can judge the public claims. It is not a compliance template, legal advice, or a claim that ClaimFlow is ready for production or real data. The domain model, API guide, testing guide, and AWS architecture remain authoritative for behavior and design; deployment evidence is detailed in [the AWS architecture](aws-architecture.md) and [the testing guide](testing.md), and resource settings in [the infrastructure README](../infrastructure/README.md).

## Scope and operating model

- **Public source, fabricated data.** The source is published as a portfolio and demonstration. The deployment and the local runtime hold only fabricated people, claims, comments, and receipts. No real employee, financial, or receipt data is used, and none may be added.
- **No self-registration.** The operator creates accounts; the Cognito user pool has self-service sign-up disabled.
- **Not a service.** There is no commercial service, production-readiness claim, SLA, customer-support commitment, or compliance claim.
- **Manual, low-cost AWS deployment.** The operator deploys the stack and publishes the web files by hand, in one environment and Region.

Because of this scope, the enterprise controls that apply to real users, real personal data, commercial operation, or production use are **not** being claimed. They are not marked complete anywhere in this record; they are summarized under the trigger that would make them necessary ([Triggers for further work](#triggers-for-further-work)).

## Evidence standard

An item counts as done only when something reproducible or independently inspectable shows it: a file in the repository, a test, a command whose method and scope are recorded, or a dated manual observation with its limits. "The code looks correct," a high test count, "AWS handles it," or a tool's silence is not evidence. Each claim below carries its method and limits; where a check was not run, it says so.

## Local development sign-in: CSRF assessment (9 November 2026)

**Scope.** The local runtime signs a user in with a signed cookie (`claimflow_session`, `HttpOnly; SameSite=Strict; Path=/`), with no password; it is development-only. The deployed AWS path is separate: it authenticates with a Cognito Bearer token validated by API Gateway and uses no cookie, so it is not assessed here.

**What protects mutations (source, 9 November 2026).**

- `SameSite=Strict` keeps the cookie off cross-site requests. It does **not** separate different ports on the same host: `localhost:5174` and `localhost:3911` are the same site, so a page on another local port is cross-origin but still gets the cookie. Cookies are also shared across ports.
- Every `POST`, `PATCH` and `DELETE` business mutation is idempotent and requires an `Idempotency-Key` header. A browser cannot add that header to an HTML form or a no-CORS request; a script that adds it triggers a CORS preflight.
- On JSON routes, a non-empty request body must be `application/json` (checked before the mutation), so browser-permitted cross-site content types (form-urlencoded, multipart, text/plain) are rejected there. The raw receipt upload (`POST /receipts`) is not a JSON route: it accepts other content types and is protected by the custom `Idempotency-Key` header, not by a content-type check.
- The server sends no `Access-Control-*` header and has no `OPTIONS` route, so a preflight gets 404 and the browser blocks the actual request; a cross-origin page cannot read any response.
- Development sign-in and sign-out (`PUT` and `DELETE /session`) do not require `Idempotency-Key`. Sign-in requires a JSON body; sign-out does not. Both methods require a browser preflight when sent cross-origin, and the server grants no CORS permission.

**Evidence.**

- Automated (HTTP level, `services/api/test/csrf-local-session.test.ts`, 12 tests, synthetic data, cookies redacted): the cookie attributes; cross-site-shaped requests with the victim cookie and an `Origin` header using form-urlencoded, multipart and text/plain bodies (including a JSON body labelled text/plain and an empty form) are refused with 400 and leave the claim list and a draft claim's status unchanged; the JSON content-type check refuses such requests even if the custom header were present; a text/plain `PUT /session` signs nobody in; preflights get 404 with no CORS headers and no response carries any `Access-Control-*` header; the legitimate flow (sign in, JSON mutation with the header, sign out, sign in again) succeeds. **These prove only what the server does.** An HTTP client ignores SameSite, preflight and CORS blocking.
- Real browser (Chrome, 9 November 2026; an observation, not repeatable evidence): an isolated instance on port 3911 with a temporary data directory and the sample users (the repository's `.local` data was not used), a victim signed in through the UI, and throwaway pages on `localhost:5174` (same site, other origin) and `127.0.0.1:5175` (cross site). From the same-site origin, top-level form posts in all three encodings, an empty form, a no-CORS text/plain `POST` and a beacon reached the server with the cookie and were refused with 400; JSON `POST` with the header, `PUT`/`DELETE /session` and a credentialed cross-origin read were blocked by the browser at the preflight (eight `OPTIONS` requests, all 404) or by missing CORS permission, so no such mutation reached the server and the page could not read the response. From the cross-site origin the cookie was not sent at all (the same requests arrived anonymous, 401). Afterwards the victim was still signed in and still had only the one claim created by the control request; no forged claim existed. Controls: UI sign-in, a same-origin JSON mutation (201), switching user, and sign-out (then 401) all worked. The cookie is not readable from page script.
- Result: no reproducible bypass was found, and no application behavior was changed.

**Limits and gaps.** One browser (Chrome) and one version, on `localhost` over HTTP. The browser behavior is not asserted by an automated browser test. The server does not itself check `Origin` or `Sec-Fetch-Site`, so protection depends on browser enforcement of preflight plus the custom header and content type. DNS rebinding and a hostile page served from the same origin were not tested (the local server binds to `127.0.0.1` and checks no `Host` header). Logout CSRF cannot be sent without a preflight in current browsers but is not blocked server-side. The built web app in `apps/web/dist` (1 November 2026) was used; it was not rebuilt.

**Reassess when** (1) the cookie is used outside local development, or any cookie, session or Basic credential authenticates a deployed route; (2) a mutating route is added that is not idempotent or does not require `Idempotency-Key` or a JSON body (a `POST` that needs neither is form-submittable from a same-site page); (3) CORS headers or an `OPTIONS` handler are added, or `SameSite` is relaxed to `Lax` or `None`; (4) the JSON content-type check or the header requirement is loosened; (5) the local server is exposed beyond `127.0.0.1` or behind a shared host name; or (6) another web app is served from a local port in the same browser profile and handles untrusted content.
